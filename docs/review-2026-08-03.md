# Food Spot adversarial code review

**Review scope:** `food-spot/src`

**Review-only rule:** No file in the worktree was edited, created, deleted, moved, or formatted. This report was written to `/tmp/foodspot-review.md`, outside the repository.

## Critical

### 1. Cancelling “Delete everything” still proceeds to media deletion

**Code:** `food-spot/src/settings/settingsTab.ts:1352-1404`, cancellation set at `food-spot/src/ui/modals/progress.ts:35-39`

Cancellation only breaks the spot-note loop at line 1361. Execution then continues into media deletion and empty-folder sweeping.

**Failure scenario:** The user selects “also media,” begins deleting 100 spots, and cancels after the first. Ninety-nine spot notes survive, but their top-level cover/menu files are still trashed. The folder sweep also still runs.

## Major

### 2. Destructive media operations have no ownership boundary

**Code:** `food-spot/src/settings/settingsTab.ts:294-305`, `food-spot/src/settings/settingsTab.ts:530-590`, `food-spot/src/settings/settingsTab.ts:1371-1385`

`mediaFolder` can be any existing vault folder. Both destructive operations then treat that folder as exclusively owned by Food Spot:

- Delete-all trashes every direct file.
- “Clean up unused media” recursively trashes every file not referenced by a Food Spot, without checking whether ordinary Obsidian notes reference it.

**Failure scenarios:**

- Set `mediaFolder` to `Attachments`, which also contains `tax-return.pdf`; select “also media” during delete-all → the unrelated PDF is trashed.
- `Attachments/diagram.png` is linked from a normal note but no Food Spot → cleanup labels it unused and trashes it.

### 3. Duplicate merge discards unmodelled content before trashing the source note

**Code:** `food-spot/src/store/visitsParser.ts:79-101`, `food-spot/src/tools/duplicates.ts:240-296`, `food-spot/src/ui/modals/duplicates.ts:189-200`

The merge copies only fields represented by `FoodSpot` and parsed visits, then trashes the dropped note.

**Failure scenario:** The dropped note contains custom frontmatter, a `## Reservations` section, prose outside the managed sections, or raw text inside `## Visits`. None of that is copied into the kept note before the source is trashed.

### 4. Opening hours are dropped by imports, enrichment, updates, and restore

**Code:** `food-spot/src/types.ts:109-115`, `food-spot/src/import/pipeline.ts:189-202`, `food-spot/src/import/pipeline.ts:430-436`, `food-spot/src/ui/modals/importFlow.ts:313-341`, `food-spot/src/store/spotStore.ts:160-195`, `food-spot/src/store/noteWriter.ts:265-285`, `food-spot/src/store/backup.ts:152-177`

`hours` exists in the domain contract and Google data, but several `SpotInput` reconstruction paths omit it. `frontmatterFromInput()` treats omitted hours as `undefined`, and `applyFrontmatter()` deletes undefined keys.

**Failure scenarios:**

- Google returns opening hours during import, but the saved note receives none.
- A note has manually authored hours; toggling Favorite or changing Status calls `updateSpot()` and deletes them.
- Backup JSON contains hours; restore recreates the note without them.

### 5. “Full backup” is not content-complete

**Code:** `food-spot/src/store/backup.ts:47-69`, `food-spot/src/store/visitsParser.ts:79-127`, `food-spot/src/store/noteWriter.ts:186-190`

The backup serializes indexed `FoodSpot` objects and only embeds binaries referenced by `spot.photo` and `spot.menu`.

It therefore loses:

- Visit dish-photo binaries.
- Raw, non-visit lines inside `## Visits`.
- Any unmodelled note body or frontmatter content.

**Failure scenario:** A visit embeds `Food Spot/_media/dishes/ramen.jpg` and has a raw line such as `Parking validated`. Restore creates the visit embed but not the image, and removes the raw line.

### 6. Valid media references and read failures are silently omitted from backups

**Code:** `food-spot/src/store/backup.ts:49-58`; correct link-resolution behavior exists at `food-spot/src/settings/settingsTab.ts:546-561`

Backup uses `vault.getFileByPath(ref)` rather than Obsidian link resolution and silently catches binary-read failures.

**Failure scenarios:**

- Frontmatter contains `photo: cover.jpg`, which Obsidian resolves relative to the note to `Food Spot/_media/cover.jpg` → backup searches only for the literal vault path `cover.jpg` and omits it.
- A referenced image exists but `readBinary()` fails → export still reports success, with no indication that the “full” backup is incomplete.

### 7. Backup restore trusts arbitrary media paths and unchecked collisions

**Code:** `food-spot/src/store/backup.ts:106-136`

Every key in the imported `media` object becomes a vault write target. Paths are not constrained to `settings.mediaFolder` or checked against restored spot references. Existing destination files are skipped solely because the path exists; their content is never compared.

**Failure scenarios:**

- A crafted backup containing `media: {"Inbox/planted.html": "..."}` writes that file outside the configured media folder when the parent exists.
- The target vault already contains a different `_media/logo.jpg` → restore skips the backed-up bytes and silently points restored spots at the unrelated existing image.

### 8. Media relocation can repoint notes to the wrong files or leave broken references

**Code:** `food-spot/src/settings/settingsTab.ts:626-693`, `food-spot/src/store/spotStore.ts:74-77`, `food-spot/src/store/spotStore.ts:332-343`

There are two concrete paths:

1. Destination collisions and rename failures are skipped, but references are rewritten anyway.
2. Renaming notes removes their old index entries immediately and delays indexing the new paths. The later reference-update loop uses a fresh live index, so recently moved notes can be absent.

**Failure scenarios:**

- The destination already contains a different `photo.jpg` → the source image is not moved, but the note is rewritten to use the unrelated destination image.
- Notes are moved and temporarily disappear from the store → media moves, but their plain-string photo/menu references remain pointed at the old folder.

Nested `dishes/` directories are also not moved, although the media setting is changed and the UI reports success.

### 9. Relocation can trash arbitrary empty source-folder ancestors

**Code:** `food-spot/src/settings/settingsTab.ts:625`, `food-spot/src/settings/settingsTab.ts:650`, `food-spot/src/settings/settingsTab.ts:696-703`

Cleanup walks upward from every old parent while folders are empty. It has no boundary at the configured spots folder.

**Failure scenario:** An indexed Food Spot note lives at `Projects/Trips/Ramen.md`. After relocation, if `Trips` and `Projects` are empty, both folders can be trashed.

### 10. Fence parsing can overwrite content inside a valid Markdown code block

**Code:** `food-spot/src/store/noteWriter.ts:100-139`, `food-spot/src/store/noteWriter.ts:162-183`

Any line beginning with enough backticks or tildes is treated as a closing fence. Markdown closing fences may only have trailing whitespace, but the parser accepts lines such as `` ```not-a-close ``.

**Failure scenario:** A code sample contains `` ```not-a-close `` followed later by `## Notes`. Markdown still considers the code block open, but Food Spot considers it closed and treats the heading inside the sample as the managed section. Saving notes can replace the sample and remove later content.

### 11. Duplicate merge collapses legitimate same-day visits

**Code:** `food-spot/src/tools/duplicates.ts:160-195`

Visits are deduplicated only by date plus normalized note. Rating and spending are not part of the identity.

**Failure scenario:** One note has `{date:"2026-08-03", note:"", spent:20}` and the other has a separate visit `{date:"2026-08-03", note:"", spent:80}`. Merge produces one visit and discards the second spend, rating, and visit count.

### 12. Full-record updates race and overwrite unrelated changes

**Code:** `food-spot/src/store/spotStore.ts:160-195`, `food-spot/src/store/spotStore.ts:332-343`

Every partial update is rebuilt from the indexed snapshot and written as the complete managed frontmatter schema.

**Failure scenarios:**

- Favorite and status updates begin concurrently from the same snapshot. Whichever full write finishes last restores the other field’s old value.
- A user externally edits the phone number, then toggles Favorite before the delayed reindex completes → the Favorite write restores the stale indexed phone number.

### 13. Clearing or changing Discover input does not invalidate an in-flight search

**Code:** `food-spot/src/ui/tabs/discover.ts:259-275`, `food-spot/src/ui/tabs/discover.ts:357-397`

`dropResults()` does not increment `searchGen`. Manual clearing only invokes it when results already exist, and another search cannot start while `loading` is true.

**Failure scenario:** Start a Rotterdam search, then clear the location or replace it with Amsterdam before Google responds. The Rotterdam response still passes the generation check and repopulates results beneath the blank or Amsterdam input.

### 14. Browser Fetch can save after cancellation and advance its queue twice

**Code:** `food-spot/src/ui/modals/browserFetch.ts:109-155`, `food-spot/src/ui/modals/browserFetch.ts:161-174`

There is no `done` check after `executeJavaScript()` resolves.

**Failure scenario:** Close the modal while extraction is awaiting. `onClose()` reports cancellation and advances the queue. The old extraction then resumes, writes the rating, and calls `onFinished(true)`, advancing the same queue a second time.

A related failure exists at lines 123-144: `done` is set before `updateSpot()`. If that write rejects, the catch schedules another poll, but the poll immediately returns because `done` is already true. The modal remains stuck with no error and the queue never progresses.

### 15. Several rating-source URL edits display “Saved” but are discarded

**Code:** `food-spot/src/ui/modals/addEdit.ts:665-686`, `food-spot/src/ui/modals/addEdit.ts:890-914`, `food-spot/src/ui/modals/addEdit.ts:1101-1116`

`sameExternal()` omits Facebook, OpenTable, and Eet.nu fields.

**Failure scenario:** Change only `facebookUrl`, `opentableUrl`, or `eetnuUrl` and press Save. The comparison reports no external change, the update omits `external`, and the modal reports success without persisting the edit.

### 16. Open-now uses the computer’s timezone, not the restaurant’s

**Code:** `food-spot/src/ui/components/hours.ts:113-150`, with no timezone field in `food-spot/src/types.ts:82-134`

`getDay()`, `getHours()`, and `getMinutes()` use the machine’s local timezone.

**Failure scenario:** At Amsterdam 18:00/New York 12:00, a New York restaurant with `Mon 12:00-14:00` is evaluated as 18:00 and shown closed while it is open.

### 17. UTC conversions misdate local calendar values

**Code:** `food-spot/src/store/legacyMap.ts:46-49`, `food-spot/src/ui/modals/quickAdd.ts:22-24`, `food-spot/src/ui/components/card.ts:33-42`, `food-spot/src/ui/tabs/dashboard.ts:31-45`

Calendar dates are generated with `toISOString().slice(0, 10)` and parsed with `new Date("YYYY-MM-DD")`/`Date.parse()`, both of which use UTC semantics.

**Failure scenarios:**

- In UTC−7 at local `2026-08-02 18:00`, the generated “today” value is `2026-08-03`.
- Parsing `2026-08-02` produces UTC midnight, locally August 1 at 17:00, so a visit on the current local calendar day can display as “yesterday.”

### 18. Standalone guide HTML permits executable URL schemes

**Code:** `food-spot/src/import/jsonld.ts:303-305`, `food-spot/src/import/importers.ts:367-377`, `food-spot/src/ui/modals/importFlow.ts:313-341`, `food-spot/src/tools/guideHtml.ts:73-76`, `food-spot/src/ui/modals/cityGuide.ts:137-140`

HTML attribute characters are escaped, but URL schemes are not restricted.

**Failure scenario:** A spot contains `url: javascript:...`, whether imported from JSON-LD or manually authored. The standalone exported HTML contains that value in an `<a href>`, and the JavaScript executes when the recipient clicks it.

### 19. PDF export leaves private guide HTML in the OS temp directory

**Code:** `food-spot/src/tools/pdfExport.ts:42-45`, `food-spot/src/tools/pdfExport.ts:81-100`

The self-contained guide HTML—including restaurant details and base64-encoded photos—is written to a timestamped temporary file. Cleanup removes only the webview; it never deletes the file.

**Failure scenario:** Every successful, failed, or timed-out PDF attempt leaves a readable `foodspot-guide-*.html` file until the OS eventually cleans it.

## Minor

### 20. Visit photo aliases and dimensions do not round-trip

**Code:** `food-spot/src/store/visitsParser.ts:23`, `food-spot/src/store/visitsParser.ts:57-63`, `food-spot/src/store/visitsParser.ts:104-115`

**Failure scenario:** `![[dish.jpg|300]]` or `![[dish.jpg|Dinner]]` becomes `![[dish.jpg]]` after visits are rewritten.

### 21. Delete-all’s media option ignores nested dish photos

**Code:** `food-spot/src/settings/settingsTab.ts:1371-1385`, `food-spot/src/ui/components/dishPhotos.ts:46-64`

Only direct `TFile` children are trashed.

**Failure scenario:** The user selects the media option and Food Spot trashes top-level covers and menus, but every file under `mediaFolder/dishes/` survives. The final notice does not report the omission.

### 22. Early PDF failures reject without a user-facing error or print fallback

**Code:** `food-spot/src/tools/pdfExport.ts:75-91`, `food-spot/src/ui/modals/cityGuide.ts:125-135`

Save-dialog and temp-file failures occur before the promise-local failure handler. The caller has no `.catch()`. Print fallback also runs only when Electron is entirely unavailable, not when `printToPDF()` exists but fails.

**Failure scenario:** The save dialog rejects, the temp directory is unwritable, or `printToPDF()` fails. The button resets, but the user receives no useful fallback and some early failures produce an unhandled rejection.

### 23. Enrichment photo failures are reported as “skipped”

**Code:** `food-spot/src/import/pipeline.ts:450-455`, `food-spot/src/import/pipeline.ts:509-541`

**Failure scenario:** Run enrichment with only Photo selected and let the download fail. The exception is discarded, the result is `null`, and bulk enrichment counts the spot as skipped rather than failed.

### 24. Discover can leak object URLs after teardown

**Code:** `food-spot/src/ui/tabs/discover.ts:145-169`, `food-spot/src/ui/tabs/discover.ts:648-655`

A photo request can finish after `destroy()` has revoked and cleared the cache.

**Failure scenario:** Destroy the Discover tab while a Place Photo request is pending. The completed request creates a new object URL, stores it in the already-cleared cache, and renders into detached DOM. No later teardown revokes that URL.

### 25. Negative visit spending is accepted despite `min="0"`

**Code:** `food-spot/src/ui/modals/logVisit.ts:95-136`

The handler only rejects `NaN`; it never checks validity or requires `spent >= 0`.

**Failure scenario:** Enter `-5` and save → `spent: -5` is written.

### 26. Invalid `24:xx` opening times are accepted and wrapped

**Code:** `food-spot/src/ui/components/hours.ts:48-62`

Only `24:00` is valid ISO-style midnight notation, but `24:30` is accepted as 1,470 minutes and later formatted as `00:30`.

**Failure scenario:** Store `Mon 24:30-01:00`. The parser accepts it and later presents the invalid opening time as a plausible `00:30` value.

## Missing coverage

The current smoke bundle at `food-spot/tests/smoke.test.mjs:38-50` does not include several pure or mostly pure modules where these regressions deserve focused tests:

- `food-spot/src/tools/duplicates.ts` — destructive merge planning.
- `food-spot/src/tools/guideHtml.ts` — URL-scheme validation and escaping.
- `food-spot/src/ui/components/hours.ts` — overnight ranges, invalid times, timezone assumptions, and week rollover.
- `food-spot/src/import/importers.ts` — URL assignment and provider mapping.
- `food-spot/src/import/sourceDiscovery.ts`.
- Pure helpers in `food-spot/src/import/pipeline.ts`.

The source-text guard for `SpotInput` merge fields also does not check `hours`, allowing that contract drift to remain green.

## Checked and CLEAN

### Note and storage safety

- Normal managed-section replacement preserves body content before and after the section.
- Unknown frontmatter keys on the kept note survive ordinary updates because only known supplied keys are changed.
- Properly closed backtick and tilde fences correctly hide headings from managed-section detection.
- Nonblank raw lines in the kept note’s `## Visits` survive normal add/update/delete operations.
- New-note creation uses collision-safe numbered filenames rather than overwriting an existing note.
- Ordinary spot deletion uses Obsidian trash, not permanent deletion.
- Delete-all requires exact `DELETE` confirmation.
- Restore rejects malformed JSON and files without the Food Spot backup marker.
- Restore records per-spot and per-media errors rather than aborting the whole run.

### Merge behavior

- Cuisines, tags, and visit photo paths are unioned.
- Kept-note Notes content is combined with modelled Notes from the dropped record.
- External rating and count values are transferred together.
- The dropped note is trashed only after the kept-note update resolves.

### Obsidian API lifecycle and UI cleanup

- Main store listeners are registered through `registerEvent`.
- Virtual grid/list resize observers, animation frames, and scroll listeners are cleaned up.
- Leaflet map observers and map instances are removed.
- Gallery `IntersectionObserver` is disconnected on close.
- Autocomplete listeners and blur timers are removed.
- Filter-panel document listeners are removed.
- The main view unregisters its document data-change listener and destroys mounted tab handles.
- Add/Edit Places search and List Import use generation checks against stale responses.
- Visit edit/delete actions re-resolve the original visit instead of trusting a stale visible index.

### Security and privacy

- No `innerHTML`, `insertAdjacentHTML`, `document.write`, or equivalent raw-HTML DOM sink was found under `food-spot/src`.
- Guide text fields are HTML-escaped.
- The guide preview iframe is sandboxed without `allow-scripts`.
- PDF webview Node integration is disabled.
- Guide images come from caller-generated data URIs rather than raw note strings.
- The Google API-key UI clearly discloses plaintext local storage and uses a masked input.
- No API-key inclusion in backups, exports, diagnostics, or logs was found.
- Google requests use fixed Google hosts; no user-controlled host receives the key.
- Normal new spot notes, downloaded Google photos, dish photos, city-guide notes, diagnostics, and discovery logs derive their destinations from configured folders.
- Writes outside the vault use explicit system save dialogs.

### Other correctness checks

- Same-timezone overnight opening ranges and closing boundaries behave consistently.
- Search sort keys are normalized; no mixed-type comparator defect was found.
- Existing target notes are checked before note relocation.
- Existing media files are not overwritten during restore, although silently accepting conflicting content is finding 7.
- Normal virtual-card photo unmounts release lazy-photo resources.
- Map and gallery observer teardown paths are present.
